القرار التنفيذي

التطبيق غير جاهز للإطلاق التجاري. النسخة المسلّمة نسخة معالجة للمخاطر وتطوير محلي، وليست نظام حجز مكتملًا. المشكلة الأساسية لم تكن الألوان: هوية المسافر كانت تُنشأ محليًا داخل مستخدمي الشركة، وقواعد قاعدة البيانات كانت تسمح للجميع بالقراءة والكتابة، وبعض الشاشات كانت تؤكد عمليات لم تحدث فعلًا.

تم تعديل المصدر نفسه، وإضافة اختبارات انحدار، وتحديث ملف تثبيت الاعتماديات. لم يتم نشر التغييرات أو تعديل إعدادات Firebase الحية أو إرسال رسائل أو إجراء مدفوعات. إغلاق القواعد في الملفات لا يحمي مشروعًا منشورًا إلا بعد نشرها عليه.

نطاق المراجعة وحدودها

  • تم جرد ملفات الأرشيف ومراجعة نقاط الدخول والهوية والتخزين والمزامنة والتسعير والاستيراد والتصدير والشاشات المرتبطة بها. جدول مستقل audit/file-review.csv يسجل كل ملف وحالة تغييره وإشارات الفحص والاختبارات المطلوبة.
  • القراءة والفحص الساكن لا يعادلان اختبار كل شاشة فعليًا. الملفات الثانوية موضحة كفحص ساكن، ولم تُوسم زورًا بأنها اختُبرت بصريًا.
  • لم يتوفر مشروعان معدّان للمصادقة أو حسابات اختبار أو مفاتيح دفع. لذلك لم نختبر وصول البريد أو Google OAuth أو إلغاء جلسة من لوحة Firebase فعليًا.
  • محاولة تشغيل Playwright تعثرت لغياب Chromium وفشل تنزيله. لا توجد لقطات شاشة معتمدة ولا ادعاء بمراجعة بصرية مكتملة. يلزم اختبار RTL ولوحة المفاتيح والموبايل قبل الإطلاق.

أهم المشاكل وما حدث لها

P0: مانع إطلاق/كشف بيانات أو تجاوز هوية. P1: فقد بيانات أو نتائج مضللة أو خلل تشغيلي مؤثر. P2: جودة استخدام وصيانة وأداء. «متوقف» تعني منع السلوك الخاطئ، ولا تعني بناء الخدمة البديلة.

ما يعمل الآن وما لا يعمل

  • يعمل بعد الإعداد: تدفق دخول بالبريد برابط تحقق أو Google، وفصل بوابتي الهوية. لم يتم إرسال رسائل تحقق أثناء التدقيق.
  • يعمل محليًا لمستخدم شركة له claims صحيحة: الواجهات التشغيلية المتبقية، التحرير المحلي، CSV والتحقق من الأسعار، التصدير والمعاينة. لا يوجد تزامن فريق موثوق.
  • متوقف عمدًا: API التجاري، نشر شركات، قبول عروض من العميل، مشاركة رحلات عامة، استلام استفسارات عامة، الدفع، دعوات وصلاحيات من المتصفح، الاستعادة غير المتحققة، تسجيل الحج والعمرة والمستندات، واستخراج PDF/XLSX الوهمي.
  • حساب المسافر يستطيع الدخول لكن ربط الحجوزات الفعلية غير مبني؛ لا تُعرض رحلات شركة محلية له.
  • المشروع لا يجمع وثائق عبر مسار التسجيل الجديد. مخططات قديمة optional في types/index.ts وبعض أدوات التصدير الثانوية تحتاج تنظيفًا إضافيًا قبل إعادة تفعيل الوحدات القديمة. حذف مخطط قديم لا يحذف بيانات سبق تخزينها؛ يحتاج ذلك ترحيلًا ومراجعة منفصلة.

الأكواد المعدلة وكيف تطبقها

الأرشيف يحتوي المشروع كاملًا، وليس مقتطفات فقط. audit/changes.patch يوضح الفروق مع النسخة المرفقة، وaudit/changed-files.txt قائمة الملفات المعدلة. استخدم المشروع في فرع تجريبي، ولا تطبّق الملف patch والمشروع الكامل معًا.

المنع عند غياب الخدمة، من server.ts:

app.use('/api', (_req, res) => {
  res.setHeader('Cache-Control', 'no-store');
  res.status(503).json({
    error: 'SERVICE_NOT_READY',
    message: 'الخدمة غير متاحة حاليًا. لم يتم إرسال أو حفظ الطلب.'
  });
});

عزل التخزين، من sessionScope.ts:

export function operatorStorageKey(key: string): string {
  if (!scope) throw new Error('Operator session required');
  return `daleel:operator:${scope}:${key.replace(/^qde_/, '')}`;
}

قراءة لا تتلف بيانات الآخرين، من storage.ts:

getInquiries(workspaceId: string): Inquiry[] {
  const list = getStorageItem<Inquiry[]>(STORAGE_KEYS.INQUIRIES, []);
  return list.filter(i => i.workspaceId === workspaceId);
}

قواعد الإغلاق المؤقت، وليست قواعد تشغيل إنتاج:

match /{document=**} { allow read, write: if false; }

لا يجوز استبدالها بـ allow-all لتجاوز خطأ شاشة. فتح القاعدة يتطلب سياسة ملكية واختبارات Emulator. استخدام Firebase مشروعين مستقلين يمنع اشتراك هوية المسافر والشركة؛ متغير mode يختار واجهة ولا يمنح صلاحية.

خطوات التشغيل

  1. استخدم Node 22.14 أو أحدث متوافقًا مع متطلبات الاعتماديات، ثم npm ci.
  2. انسخ .env.example إلى .env.local لواجهة Vite، وأدخل بيانات مشروع Firebase منفصل لكل بوابة. هذه إعدادات عميل؛ لا تضع service account أو مفتاح AI سريًا داخل متغير VITE.
  3. فعّل Email Link وGoogle، واضبط Authorized Domains وعنوان الرجوع HTTPS لكل مشروع. رابط البريد يطلب تأكيد نفس البريد عند إكمال الدخول.
  4. أنشئ عضوية مشغّل حقيقية عبر Admin SDK آمن وأضف claims workspaceId وrole. لا يوجد زر في العميل يمنح Owner. لا تستخدم مشروع Firebase القديم تلقائيًا.
  5. شغّل npm run lint ثم npm test ثم npm run build. للتطوير npm run dev؛ لتشغيل بناء Node استخدم NODE_ENV=production npm start وفق نظام التشغيل.
  6. قواعد Firestore تحتاج نشرًا إلى المشروع الصحيح. لا توجد حاجة لفتح Firestore لتشغيل المعاينة المحلية؛ جميع APIs التجارية مغلقة حاليًا.
  7. احتفظ بنسخة من بيانات الإصدار القديم قبل الترقية. لم نرحّل مفاتيح التخزين القديمة إلى الحساب الجديد لأن نسبتها لصاحب صحيح غير مضمونة.

سجل التحقق

  • TypeScript: تشغيل tsc --noEmit؛ السجل audit/typecheck.txt.
  • اختبارات 17 حالة للتسعير/تفسير الاستفسار، و8 حالات انحدار للعزل/الحفظ/CSV/FX والسعة؛ بالإضافة إلى مجموعات الإضافات والحج وvoucher وconcierge. السجل النهائي audit/tests.txt هو المرجع للنتيجة.
  • عُدلت التوقعات القديمة التي كانت تشترط كتالوجًا وهميًا أو طباعة رقم ترخيص/ضريبة. البيانات المصطنعة داخل اختبارات الحساب تظل fixtures للاختبار، وليست بيانات تُعبأ في الإنتاج.
  • البناء: audit/build.txt مع تحذير حجم حزمة B2B المتبقي. لا يُفسَّر نجاح البناء بأنه جاهزية تشغيلية.
  • HTTP محلي: /health يعمل، وثلاثة مسارات API قديمة تعيد 503 وJSON، ومسار واجهة الشركة يعيد التطبيق. التفاصيل audit/http-tests.json.
  • غير منفذ: OAuth/Email end-to-end، Firestore Emulator، اختبارات اختراق، مدفوعات، نشر فعلي، استعادة نسخة احتياطية، تجربة Safari/iOS، ومراجعة بصرية فعلية. تنزيل Chromium فشل؛ هذا نقص في التحقق لا نتيجة نجاح.

P0 / الهوية والبيانات Backend متعدد الشركات، verifyIdToken، عضويات server-side، RBAC لكل عملية، قاعدة بيانات دائمة حساب شركة A لا يقرأ أو يعدل سجل B بتغيير المعرف؛ المسافر لا يستقبل cost أو margin أو قائمة ضيوف الآخرين؛ اختبارات رفض واضحة.
P0 / المسافر حفظ حساب مسافر أدنى وربط travelerId بالحجز؛ جلسات مستقلة ومحو بيانات الشاشة عند الخروج نفس البريد في البوابتين لا يمنح عضوية تلقائيًا؛ refresh والخروج والتبديل وانتهاء الجلسة مختبرة.
P0 / الطلب والعرض طلب فعلي، quote version immutable، قواعد انتقال status، قبول idempotent لا يُعرض «تم الإرسال/القبول» إلا بعد نجاح خادمي؛ النقر المزدوج لا ينشئ طلبين؛ فشل الشبكة لا يفقد المسودة.
P0 / المشاركة رمز عشوائي طويل محفوظ hashed، انتهاء وإلغاء، DTO محدود رمز خاطئ/منتهي لا يعيد أي رحلة؛ لا توجد تكلفة داخلية في Network أو HTML؛ لا يمكن enumerate الحجز.
P0 / التسعير تثبيت FX ومصدره وتاريخه، تكلفة غرفة/شخص واضحة، rate versions، سياسة الأطفال والإضافات إعادة فتح نفس إصدار العرض تعطي المجموع نفسه؛ تغيير العملة أو العدد يبطل override غير المتوافق؛ لا تأكيد لسعر منتهي أو غير موجود.
P0 / الدفع Hosted checkout، webhook signature، idempotency، reconciliation/refunds لا تدخل PAN/CVC إلى خادم دليل؛ redirect نجاح العميل لا يساوي Paid؛ إجمالي الطلب يحسبه الخادم.
P1 / النزاهة migrations، schema validation، نسخ احتياطية واختبار restore وتعارض تعديلات استرجاع نسخة في بيئة اختبار دون تغيير صاحبها؛ أي فشل حفظ يظهر للمستخدم؛ إصداران متزامنان لا يطغى أحدهما على الآخر بصمت.
P1 / الواجهة مراجعة 360/390/768/1440px، RTL/EN، tab/focus، قارئ شاشة، حالات offline/error/empty لا overflow أفقي؛ جميع النوافذ تحفظ وتستعيد focus؛ عناصر التحكم تعمل بالكيبورد؛ لا بيانات أو نجاح مختلق.
P1 / التشغيل سجلات أخطاء بلا أسرار، مراقبة API، rate limits على المستخدم/IP، تنبيهات، سياسة احتفاظ وحذف حساب trace ID لكل فشل؛ لا بيانات حساسة في logs؛ تحديد دور الاستجابة وتوقيت التنبيه؛ حذف حساب قابل للتحقق.
P2 / الأداء تقسيم تبويبات B2B، تحميل الخرائط عند الطلب، pagination قياس فعلي على موبايل وشبكة متوسطة؛ تحميل المسافر لا يحمل شيفرة لوحة التشغيل.

ابدأ بإطلاق تجريبي محدود بعد إغلاق P0، مع رحلات حقيقية قليلة ومراجعة يدوية. لا تجمع وحدات ERP وmarketplace والدفع والسياحة الدينية كلها في الإصدار الأول.

المنافسة: أين فرصة دليل؟

بحسب موقع Trio Travel الرسمي، منتجهم يعلن تشغيل الشركات والحسابات والتقارير وربط أنظمة الحجز وإدارة النقل والحج والعمرة. هذه معلومات تسويقية منشورة وليست اختبارًا مستقلًا لجودة التنفيذ. لم أجد في الصفحات التي راجعتها رقمًا موثقًا للعملاء يصلح للمقارنة.

المصدر: https://trio-travel.com/ و https://etolv.com/trio-travel.php?lang=en — تمت مراجعتهما في 22 أكتوبر 2026.

لا يوجد دليل كافٍ لقول إن ميزة محددة «عندك ومش عندهم». الموجود في دليل الآن نواة واجهات لبناء العرض والبرنامج والتشغيل؛ أغلب رحلة المسافر الكاملة ما زالت تحتاج Backend. فرصة المنافسة المقترحة هي إنجاز رحلة العميل من طلب إلى عرض واضح إلى متابعة يومية، ثم قياس قيمتها مع الشركات الصغيرة، وليس الادعاء بتفوق ERP قبل وجود محاسبة موثوقة.

التجربة المقترحة لماذا قد يختارها العميل؟ micro-interactions مقياس اختبار
طلب رحلة في 60–90 ثانية: وجهة، موعد، عدد، ميزانية اختيارية يقل الاحتكاك وتصل للشركة متطلبات مفهومة progress مختصر، حفظ مسودة، سؤال واحد عند نقص معلومة، رسائل خطأ بجانب الحقل اكتمال الطلب، زمن أول رد مؤهل
عرض تفاعلي عربي/إنجليزي بإجمالي واضح وما يشمله يقل السؤال المتكرر وعدم الثقة تغيير عدد المسافرين يعطي فرق السعر قبل التأكيد؛ حالة السعر وتاريخ صلاحيته مشاهدة → قبول مؤهل، عدد رسائل التوضيح
مشاركة برنامج مع مرافقين للتصويت على اختيارات محددة سبب طبيعي لدعوة أشخاص جدد رابط محدود الصلاحيات، تصويت دون كشف سعر الشركة أو بيانات الحجز نسبة المشاركات التي تنتج مستخدمًا فعليًا
«يومي في الرحلة»: موعد ومكان التجمع وجهة اتصال معيّنة قيمة يومية بعد البيع إشعار تغيير برنامج موثق، إضافة للتقويم، مؤشر آخر تحديث، offline subset محدود فتح البرنامج أثناء الرحلة، انخفاض مكالمات الاستفسار
WhatsApp بموافقة العميل وقوالب رسمية عند تفعيل التكامل القناة مألوفة محليًا وتسرع الرد فتح محادثة بنص جاهز دون إرسال تلقائي؛ لاحقًا delivery status حقيقي زمن الرد ونسبة إكمال الطلب، opt-out
تنبيه للشركة بالعروض التي تحتاج متابعة دون قياس وهمي يربط المنتج بالمبيعات لا بالاستعراض مهمة متابعة واضحة، إيقافها تلقائيًا عند الرد، undo للإجراءات القابلة للعكس قبول العروض وزمن إعداد عرض صحيح
تقييم بعد رحلة مكتملة وإحالة بعد اكتمال الخدمة ثقة قابلة للتحقق ونمو دون سبام طلب تقييم اختياري، مكافأة إحالة بعد تأكيد العملية وضبط الاحتيال مراجعات مرتبطة بحجوزات، تكلفة اكتساب وإحالات مؤهلة

هذه فرضيات منتج قابلة للاختبار، وليست وعود نمو. ابدأ بثلاث شركات فعلية ومجموعة مسافرين، وسجّل أسباب تعثر الطلب والاعتراض على العرض قبل بناء مزيد من الشاشات. لا تعتمد عدد الزيارات وحده؛ قِس الطلب المؤهل، سرعة العرض الصحيح، الحجز المؤكد، وعودة الشركة لاستخدام المنتج أسبوعيًا.
