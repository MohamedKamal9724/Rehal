# Backend Migration Plan: localStorage → production

Goal: move Daleel Egypt from a single-browser prototype to a multi-tenant service where pricing, permissions and public proposal links are enforced on the server.

Items marked **(recommendation)** are judgment calls with reasoning; the rest follow directly from the current code.

## 1. Principles

1. **The server is the only source of truth for prices.** The client may preview, but every saved/sent quote is re-priced server-side from the rate library using the same rules as `pricingEngine.ts`.
2. **Tenant isolation in the database, not in the UI.** Every row carries `workspace_id`; the database refuses cross-tenant reads.
3. **Keep the `repository` seam.** `src/lib/storage.ts` already exposes `getX / saveX` per entity. Replace its implementation with API calls; components should barely change.
4. **No money handling** stays a hard product rule (see README).

## 2. Database choice (recommendation)

**PostgreSQL with Row-Level Security** (e.g. managed Postgres), rather than Firestore.

Why: the data is relational (rates ↔ suppliers ↔ seasons ↔ quote lines), reporting needs joins and aggregates (margin by agent, win rate by source), and RLS gives tenant isolation as a database guarantee. Firestore would work for storage, but cross-entity analytics and rate versioning get awkward. The README lists either as acceptable; this is the one I'd pick.

Hosting region: choose one close to Egypt/EU for latency; check Law 151/2020 data-transfer rules with counsel before choosing (see §7).

## 3. Schema mapping

Types in `src/types/index.ts` map one-to-one to tables. Notes only where the mapping is not obvious:

| Type | Table | Notes |
|---|---|---|
| Workspace, User | `workspaces`, `memberships(user_id, workspace_id, role)` | A user can belong to several workspaces; role lives on the membership. |
| Rate | `rates` + `rate_versions` | Keep `version`; never UPDATE a price in place, insert a new version and point `rates.current_version` at it. Quotes store the `rate_version_id` they used. |
| Season | `seasons`; `rate_seasons` join | Replaces `seasonIds: string[]`. |
| ExchangeRate | `exchange_rates` | Make pricing read this table (today it reads constants). |
| Inquiry | `inquiries` | `raw_text` stored sanitized; keep original only if counsel agrees. |
| Quote / QuoteDay / QuoteLine | `quotes`, `quote_days`, `quote_lines` | Persist the computed breakdown (`cost_egp`, `price_egp`, `fx_snapshot`, `rate_version_id`, `status`) so an old quote never changes when rates change. |
| ProposalViewEvent | `proposal_views` | Written only by the public route. |
| FollowUpTask | `follow_up_tasks` | Generated by a job, not on every view. |
| AuditLog | `audit_log` (append-only) | Insert-only role; no UPDATE/DELETE grants. |

Money columns: `numeric(14,2)`, never float. Dates as `date`/`timestamptz`.

## 4. API surface

Minimum set (REST/JSON, all under auth except §4.2):

- `POST /auth/*` (use a managed provider; see §5)
- `GET/POST/PATCH /rates`, `/suppliers`, `/seasons`, `/exchange-rates`
- `POST /rates/import` (spreadsheet) and `POST /rates/import/pdf` → creates a **draft import** for human review before anything becomes a rate
- `POST /inquiries`, `POST /inquiries/:id/parse` (wraps the existing Gemini call, with credits metering)
- `POST /quotes/price` — body: lines + group + currency + travel dates → server-computed result (used for live preview)
- `POST /quotes`, `POST /quotes/:id/send`, `POST /quotes/:id/approve`
- `GET /follow-ups`, `PATCH /follow-ups/:id`
- `GET /analytics/*`

### 4.1 Server-side rules that replace today's client checks

- `send` rejects if any line is `Rate missing`/`Expired rate` (recomputed server-side).
- `send` rejects if `margin < workspace.minMarginPercent` and the quote has no approval by an Owner/Admin.
- Net-cost fields are **omitted from responses** for roles that must not see them (not just hidden in the UI).
- Each mutation writes an audit-log row in the same transaction.

### 4.2 Public proposal route

- `GET /p/:token` (no login). Token = ≥128-bit random, stored hashed; expires with the quote's `validUntil`; revocable.
- Returns a **sell-side projection only**: no cost, margin, supplier names unless the workspace opts in.
- Records a view (`proposal_views`) with real device type and real time-on-page measured client-side (beacon on page hide). Bots/link-preview crawlers (WhatsApp, Slack unfurls) must be excluded by user-agent, or every shared link will look "viewed".
- The React app already has `ProposalViewer` with a `trackView` prop for exactly this route.

## 5. Auth and RBAC

- Use a managed identity provider (email + password, magic link, optional Google). Do not hand-roll auth.
- Roles stay `Owner / Admin / Sales Agent / Operations / Viewer`; define them as a permission matrix in one server file (e.g. `can('quote:send')`) and test it. Suggested starting matrix: Viewer read-only; Sales Agent create/send quotes, no net costs if toggle on; Operations manage rates/suppliers; Admin + approvals + team; Owner + billing display + workspace deletion.
- Remove the in-UI role switcher from production builds.
- Rate-limit and authenticate `/api/ai/*`; meter against `aiCreditsLimit` server-side.

## 6. Integrations

### 6.1 WhatsApp (Meta Cloud API)
Webhook with signature verification → store message → create `Inquiry` (new or thread-appended) → enqueue parse. Needs a verified business account, approved templates for outbound messages outside the 24-hour window, and consent text. Until then keep "copy to WhatsApp" buttons.

### 6.2 Rate-sheet ingestion
Today's Excel/PDF flows are simulations. Build as: upload → parse (Excel via a library, PDF via OCR/LLM) → **staging table** → side-by-side human review → publish as new rate versions. Never write parsed prices straight into live rates. Reuse the review components.

### 6.3 Translation
`/api/ai/translate-proposal` exists but is unused. Translate stored proposal text blocks, cache by `(block_hash, language)`, and keep a per-workspace glossary of fixed names. Prices and dates are formatted by code, never translated by the model.

## 7. Compliance (needs a lawyer, not just engineers)

- Egypt Personal Data Protection Law No. 151 of 2020: lawful basis and consent for traveler data, data-subject rights, retention periods, cross-border transfer rules, and whether a DPO / registration is required. Passport numbers are already masked before AI parsing; also mask them at rest.
- Gemini processing of traveler messages: document the processor relationship and region.
- Terms of service, privacy policy, DPA template for DMC customers.

## 8. Phased delivery

Each phase should ship behind the existing UI with the prototype still working locally.

| Phase | Scope | Size | Exit criteria |
|---|---|---|---|
| 0 | Install deps, `npm run lint`, CI running `npm test` | S | Green CI |
| 1 | Postgres + RLS schema, migrations, auth, workspaces/memberships | M | Two test tenants cannot read each other (automated test) |
| 2 | Rates/suppliers/seasons/FX CRUD + versioning; swap `repository` to API | M | Prototype UI works against the API |
| 3 | Server-side pricing + quote persistence + send/approve rules + audit log | L | Server result == client preview for a shared fixture set; blocked sends tested |
| 4 | Public proposal route + real view tracking + follow-up job | M | Operator preview creates no views; crawler hits ignored |
| 5 | Inquiry ingestion: WhatsApp webhook, email, web form; parse queue with credits | L | End-to-end inquiry → parsed → quote |
| 6 | Rate import with staging/review; season, star-rating and nationality-tier rate selection | L | Importing a real supplier sheet produces reviewable drafts |
| 7 | Translation pipeline, analytics on real data, billing display → real billing (if you ever decide to) | M | — |
| 8 | Legal sign-off, security review, backup/restore drill, monitoring, then pilot DMC | M | Pilot onboarded |

Size is relative effort (S < M < L), not a time estimate.

## 9. Testing strategy

- **Golden pricing fixtures:** one JSON file of (rates, group, dates, currency → expected totals) shared by the client tests and the server tests. This is how you guarantee preview == saved price.
- RLS tests: for every table, assert a user in tenant A gets zero rows of tenant B.
- Permission matrix tests: table-driven, one row per (role, action).
- Contract tests for the public projection: assert it never contains cost fields.
- AI: record/replay fixtures for parse responses; test that malformed or injected output cannot change a price.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Client and server pricing diverge | One shared pricing module (TypeScript, imported by both) + golden fixtures |
| Wrong rate chosen silently (season/nationality/star) | Phase 6 is a prerequisite for real customer quotes; until then require agent review of every line |
| Parsed rate sheets contain errors | Staging + human approval + version history |
| Link previews inflate "views" | UA filtering + require a real interaction event before alerting sales |
| FX buffer surprises customers | Decide §7 item 1 in TECHNICAL.md before launch; show the buffer in settings |
